Hardware notes · ramips / mt7620 · compiled 2026-08-30

Getting ImmortalWrt onto a Xiaomi Mi Router 3

Why this device fell off every modern OpenWrt release, exactly what it would take to put it back, and why the work was parked.

Status: parked Backup verified Nothing flashed Running X-Wrt 26.04 · Linux 6.18.44

The port is small and well-understood — two cherry-picked commits from X-Wrt into ImmortalWrt. That part is an afternoon's work.

The risk is not. This unit has no recovery mechanism at all beyond a $3 USB-TTL serial adapter that isn't owned yet. No Breed exists for it, its USB recovery was destroyed by the current firmware, and its second kernel slot is dead. A first-ever ImmortalWrt build for a device nobody has ever built it for failing to boot is a normal outcome, not a remote one — and there would be no way back.

For a $5 used router already running current, maintained firmware, that trade wasn't worth making. Everything below is preserved so none of it needs re-researching.

Xiaomi Mi Router 3 — “R3” only. Not the 3G / 3C / 3A / 3P, which are different SoCs and share almost nothing with this.

The parallel NAND is the entire problem. Every other part of this device is ordinary ramips/mt7620 and works on current kernels. OpenWrt's Table of Hardware lists the R3 as not supported and points users at PandoraBox or X-Wrt.

Already done for you

The serial console is already enabled, with a 5-second interrupt window and the TFTP recovery IPs preconfigured. An adapter is plug-and-go — no preparatory flashing required.

mtd0 is read-only

/sys/class/mtd/mtd0/flags = 0x0        # MTD_WRITEABLE is 0x400 — not set

X-Wrt's DTS marks partition@0 as read-only, so mtd write … Bootloader returns EROFS. Any bootloader replacement has to come from U-Boot itself over serial, or from a custom build with that property removed.

03 The backup

The most valuable artifact produced by this whole exercise.

D:\r3-backup\ — all ten partitions, md5-verified OK on the PC side. Router-side tar r3-backup.tar, md5 65530a59773e0761ee32cb0bc24ad03d, 134,229,504 bytes.

Keep this even if the router is scrapped

mtd3.bin is the factory partition: 256 KB of RF calibration data and the MAC address, unique to this physical unit and unobtainable if lost. Without it the radios never come back properly. It could only be read because a working NAND driver was running at the time.

Restoring a small partition from a booted system:

mtd write /tmp/mtd3.bin factory

Note that mtd0 cannot be restored this way while running X-Wrt, for the read-only reason above.

04 Why the R3 isn't in ImmortalWrt 25.12.1

One blocker: there is no MT7620 raw-NAND controller driver in any modern tree.

ramips/mt7620 in both OpenWrt main and ImmortalWrt 25.12.1 contains zero NAND/UBI devices — every mt7620 device upstream is SPI-NOR. The directory target/linux/ramips/files/drivers/mtd/nand/raw/ holds exactly one file, mt7621_nand.c.

R3 images are absent from ImmortalWrt 21.02.7, 23.05.6, 24.10.4, 25.12.0 and 25.12.1, and present only in 18.06-k5.4-SNAPSHOT. This was never a 25.12 regression — ImmortalWrt only ever carried the R3 on its legacy branch.

Two upstream attempts, both rejected

openwrt/openwrt#597 — “Mir3 support” by ptpt52, opened 2018-01-03, closed unmerged 2018-07-25. ptpt52 subsequently founded X-Wrt, which is exactly why X-Wrt has the R3 and OpenWrt does not.

openwrt/openwrt#9344 (2022) is the substantive one. Daniel Golle:

“space limitations on other MT7620 boards … will force us to have an additional subtarget ramips/mt7620-nand … as enabling that for all mt7620 boards will break many devices. All that seemed too much effort only to allow support of basically this one device. Imho it's a good candidate for a community build.”

“the NAND driver is in very bad shape and unfit for submission upstream.”

The space concern is quantitatively real: 75 of the 137 IMAGE_SIZE declarations in mt7620.mk are 8192k or smaller.

05 What X-Wrt carries that ImmortalWrt doesn't

One 2,113-line driver that sidesteps the kernel's NAND framework entirely.

target/linux/ramips/files/drivers/mtd/maps/ralink_nand.c, plus its header. Its defining property explains both why upstream refuses it and why it never breaks:

The key property

It bypasses the Linux rawnand framework completely — its own struct ra_nand_chip, its own bad-block table, its own read/write/erase, registering a bare struct mtd_info. That is why maintainers call it unfit for upstream, and equally why it has survived 5.10 → 6.18 essentially untouched.

  • compatible = "mtk,mt7620-nand", module_platform_driver, MTD name ra_nfc.
  • Partition probes are { "cmdlinepart", "ofpart", NULL } — cmdlinepart takes priority over the device tree.
  • Carries explicit LINUX_VERSION_CODE >= KERNEL_VERSION(6,12,0) guards and a local struct nand_ecclayout replacing the one the kernel removed.
  • Lives in files/, kernel-agnostic — there is no files-* directory anywhere in x-wrt's ramips.
  • The Kconfig/Makefile hook patch is 18 lines, with variants for 6.1, 6.6, 6.12 and 6.18.

Author date 2017-11-18, committer date 2026-08-29 — x-wrt continuously rebases its whole patch stack onto current OpenWrt. This is live code, not abandonware.

ImmortalWrt's own openwrt-18.06-k5.4 branch carries the identical patch filename, with the driver embedded in the patch rather than in files/. So this is ImmortalWrt-lineage code too — a PR would be asking them to forward-port their own patch.

breed-factory.bin is two kernel copies followed by the UBI — precisely the pb-boot / Breed full-flash format.

sysupgrade case

	# this make it compatible with breed
	dd if=/dev/mtd0 bs=64 count=1 2>/dev/null | grep -qi breed && CI_KERNPART_EXT="kernel_stock"

With stock U-Boot the firmware lands in kernel (mtd8); with Breed or pb-boot present it lands in kernel_stock (mtd7) instead.

07 Corrections

Things that looked true during this investigation and are wrong. Read this before re-researching anything.

  1. “Extend mt7621_nand.c to MT7620” — does not work

    These are different IP generations, not variants. The MT7620 Programming Guide against mt7621_nand.c:

    ptpt52 only ever tested mediatek,mt2701-nfc back in 2018 — mt7621-nfc did not exist yet, but it would not have helped either.

  2. “USB recovery will save me” — not on this unit

    Scanning the whole bootloader partition for usb, fat, miwifi.bin or storage returns only uboot.bin, test.bin and saveenv help text. There is no USB stack or FAT support in this bootloader. That recovery was a feature of Xiaomi's stock system living in kernel0 + rootfs0 — which X-Wrt overwrote. It worked before X-Wrt. It does not work now.

  3. “There's a Breed for the R3” — there isn't

    breed.hackpascal.net has breed-mt7620-xiaomi-mini.bin (Mi Router Mini, SPI-NOR) and breed-mt7621-xiaomi-r3g.bin (Mi Router 3G, MT7621). The only NAND-capable Breed on the entire site is for Atheros AR9344. Flashing either wrong-device image to mtd0 is an unrecoverable brick. pb-boot is the R3's web-recovery bootloader, not Breed.

  4. “OpenWrt never had an MT7620 NAND driver” — wrong

    It shipped in-tree through kernel 4.4 with two supported boards. See section 04.

  5. “mt7620 on 6.12 has a bad WiFi regression” — fixed

    openwrt/openwrt#19128 (20–30% throughput loss from mtk_eth_soc buffer corruption setting ihl to 0) is closed and fixed, and the fix ships in 25.12.1. Not a blocker.

  6. “mt7620 is being deprecated” — no

    Still in SUBTARGETS, snapshots building 2026-08-30, with active 2026 development (PR #24557 upstream MediaTek Ethernet, #24515 PPE hardware flow offload). mipsel_24kc intact. No RAM or flash policy excludes a 128/128 device.

08 Recovery reality

Why this was parked, in one table.

PathStatus
Web recovery UI (pb-boot)possible, but requires overwriting mtd0 — the risky act itself
Breedno R3 build exists
USB recovery (miwifi.bin)gone — destroyed by X-Wrt's layout
Boot-flag fallback to slot 0dead — mtd7 holds a 2016 kernel with no rootfs
sysupgrade back to X-Wrtworks only if the flashed image boots
TTL serial + U-Boot TFTPthe only real backstop. Not owned.

If resuming, buy the adapter first

Any CH340, CP2102 or FT232 USB-TTL adapter, 3.3 V. Wiring is RX→TX, TX→RX, GND→GND, and leave VCC disconnected — the board is self-powered, and connecting VCC is a common way to kill the serial chip or the router. 115200 8N1, with a five-second window from bootdelay=5.

Serial also unlocks the correct test method: U-Boot's “Load system code to SDRAM via TFTP” boots an initramfs image entirely in RAM, so NAND enumeration and both radios can be verified without writing a single byte to flash.

One constraint — the kernel slot is 4 MiB and ramips initramfs images run around 6 MB, so initramfs testing must go over TFTP-to-RAM. It cannot be parked in kernel_stock as a fallback.

Untested free idea — never got run

The environment has bootcmd=tftp with ipaddr=192.168.1.1 and serverip=192.168.1.3. The router boots fine, so U-Boot either ignores bootcmd or tries TFTP, fails, and falls through to flash. If it's the latter, a serial-free recovery path already exists.

Test it passively: set the PC NIC to static 192.168.1.3/24, run tftpd64 with logging on, reboot the router and watch for an ARP or TFTP read request in the first ten seconds. If it asks for a file, note the exact filename — that would change the whole plan.

Payload strings confirm it is the real thing and built for this exact device: PandoraBox-Boot Version 2.1, Xiaomi R3, MT7620:CPU clock set to %dMhz, ranand_erase_write, HTTPD Recovery Module v3.0, uHttpd/1.0 PandoraBox Recovery. — with a full embedded HTML recovery UI (/upload.cgi, /config.cgi, /reboot.cgi, progress bar, English and Chinese). Web recovery is reportedly at 192.168.15.1.

Settled — write it verbatim

Do not strip the 64-byte uImage header. The stock bootloader on this unit is also uImage-wrapped with an identical header structure: same magic, same load/entry 0x80200000, same 05 05 01 00, same "NAND Fla" name. Both payloads are valid little-endian MIPS reset vectors. Confirmed by direct byte comparison.

Settled — it can't be written from X-Wrt

mtd0 flags are 0x0, i.e. read-only. The options are (a) U-Boot's own “Load Boot Loader code then write to Flash via TFTP” over serial — the correct, Linux-free route — or (b) a custom build with read-only; removed from partition@0.

coolsnowwolf/lede#8402 and #8405 are R3 users hitting infinite reboot with a yellow LED after flashing self-compiled pb-boot-format firmware. Worth noting those are firmware images flashed through pb-boot rather than bootloader bricks — arguably the system working as designed.

The tutorial's procedure targets stock firmware, not X-Wrt

D:\xiaomi mir3\ssh r3.txt holds the Xiaomi STOK exploit chain plus:

nvram set uart_en=1 / flag_last_success=1 / boot_wait=on ; nvram commit
mtd write /tmp/pbboot.img Bootloader

nvram is stock-firmware-only — X-Wrt has fw_setenv instead — and the mtd write fails on X-Wrt. The tutorial's flow is stock → SSH exploit → pb-boot. Source video (Vietnamese): youtube.com/watch?v=uazFVgpjRnk.

Why #8 fails

Two premises hold up: the bootloader reads NAND with its own driver, and a RAM-loaded kernel needs no MTD to start. The WiFi-EEPROM objection is even solvable — rt2x00 accepts ralink,eeprom-data (a raw blob in the DTB, checked before MTD) and mt76's mt76_get_of_eeprom_data() checks mediatek,eeprom-data before mtd-eeprom, with efuse fallback.

It fails on everything else. Extroot never runs under initramfs — 80_mount_root skips do_mount_root when INITRAMFS=1, so config is tmpfs and wiped every boot. root=/dev/sda2 needs a custom kernel config because SCSI, USB-storage and ext4 are kmods living in the rootfs you're trying to mount. And default_do_upgrade() writes through mtd to a named partition, so no MTD driver means no sysupgrade, permanently.

Why #9 is impossible

Six independent layers, the first one fatal: the 25.12 feeds contain only packages.adb and *.apk. Those files begin 41 44 42 64 — ASCII “ADBd”, the apk-tools v3 container. Not !<arch> (ipk), not gzip. opkg cannot read them, and bootstrapping apk means installing an .apk, which is itself ADB. The cutover is exactly at 25.12; 24.10 is still opkg.

Behind that: musl 1.1.24 versus 1.2.5 time64 symbol renames, kmod vermagic pinning, ucode-coupled netifd (21.02 has no ucode at all), ucode-only LuCI, and singleton daemons — ubusd, and procd as PID 1 — that would have to be hot-swapped.

11 Open questions

Explicitly not verified. Don't assume any of these either way.

  • Whether the passive bootcmd=tftp test shows U-Boot calling out to 192.168.1.3.
  • Whether anyone has booted an R3 on kernel 6.18 and posted a log. Adversarial research found none — the most recent first-hand confirmation located was 2025-11-19 (x-wrt issue #409, user Bob-YsPan, on an older build). This unit running 6.18.44 is itself the newest evidence that exists, which is worth mentioning if a PR is ever opened.
  • Whether the driver actually builds at 6.12 — inferred from its version guards, never compiled.
  • Whether current OpenWrt maintainers would still refuse in 2026; Golle's position is from 2022.
  • Whether the R3's NAND is BMT-formatted and would need mtk_bmt wired in for a proper driver. X-Wrt's driver rolls its own simple BBT and works, which is mildly encouraging.
  • Whether Ralink U-Boot 1.1.3 passes bootargs to the kernel, and whether the kernel would prefer it over the DTS chosen/bootargs. If yes, mtdparts=ra_nfc:… would unlock mtd0 with no rebuild, since the driver lists cmdlinepart before ofpart. Never tested; the environment currently has no bootargs at all.
  • Whether stock Ralink U-Boot will load a uImage larger than the 4 MiB kernel slot.
